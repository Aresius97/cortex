# Phase 3: Detection — CopyCatch-lite

## What this phase does

Detects the `lockstep_chargeback_ring` archetype using fixed-width time-window clustering, based on Beutel et al. (WWW 2013), "CopyCatch: Stopping Group Attacks by Spotting Lockstep Behavior in Social Networks."

**What we implement:** per-merchant chargeback timestamp extraction, a sliding time window counting distinct participating accounts, and merging of overlapping flagged windows into events.

**What we deliberately do not implement:** the original paper's local-search heuristic for optimizing the bipartite dense-block boundary. Basic time-window clustering is sufficient for this archetype's camouflage mechanism (widening jitter), and is far cheaper to build and reason about.

## A dataset gap we found and fixed before trusting any result

The dataset originally contained **zero legitimate chargebacks** — every single chargeback was ring-generated by construction. That would have made any chargeback-clustering detector score artificially perfectly, since there'd be no honest noise to separate signal from. We patched `phase1_dataset_construction/generate_dataset.py` to add 250 independent, uncorrelated organic chargebacks (`build_organic_chargebacks()`) before trusting any number from this detector. See `ENGINEERING_LOG.md` entry 6.

## Run it

```bash
python3 copycatch_lite.py --data ../phase1_dataset_construction/output --out ./results --window_minutes 30 --min_accounts 4
```

## Current results

At `window_minutes=30, min_accounts=4`: **precision 1.00, recall 0.95** (0.88 easy / 1.00 medium / 1.00 hard).

Parameter sweep (all from actual runs):

| Window | min_accounts | Precision | Recall |
|---|---|---|---|
| 1 min | 4 | — | 0.00 |
| 5 min | 4 | 1.00 | 0.56 |
| 10 min | 4 | 1.00 | 0.62 |
| 15–90 min | 3 | 1.00 | 0.95 |
| 15–90 min | 4 | 1.00 | 0.75–0.95 |
| 15–90 min | 5 | 1.00 | 0.41–0.82 |

Window width matters at the narrow end and plateaus from ~15 min onward — verified directly, not assumed, since an unresponsive parameter would suggest a stuck algorithm rather than a real result.

## An honest finding, not camouflage resistance

Easy-tier recall (0.88) is lower than medium/hard (1.00) in this run — the opposite of what you'd expect from "camouflage gets harder to catch." We checked why rather than reporting it uncritically: in this particular random draw, the easy-tier rings happen to be smaller (7-9 members) than the hard-tier rings (10-11 members), and a **fixed** `min_accounts` threshold is naturally harder for a smaller ring to clear regardless of camouflage level. This points to a real design consideration for the fusion layer: `min_accounts` should probably scale relative to something (e.g. a fraction of typical ring size, or be chosen via the cost-sensitive framework in `docs/PROJECT_DOCUMENTATION.md` §6) rather than being a flat constant — noted here rather than smoothed over.
